在音視頻系統中，frame 在編碼層面是影像資料；在播放與同步層面，frame 同時承載明確的時間語意。

<!-- truncate -->

在前面的文章[^1]，曾提及過 Frame 以及 Timestamp 的概念。Frame rate 定義了 frame 產生的節奏；frame duration 描述相鄰 frame 的實際時間間隔；PTS（Presentation Timestamp）與 DTS（Decoding Timestamp）則負責告訴系統「何時解碼」與「何時顯示」。只要這些時間關係處理不當，即使編碼與傳輸本身正確，畫面仍會出現抖動、倒序或與音訊不同步的問題。

在 ffmpeg 中，[AVPacket](https://ffmpeg.org/doxygen/8.0/structAVPacket.html) 用來表達一段壓縮後、尚未解碼的位元資料，加上時間與附屬資訊。demuxer 處理過後，decoder 處理之前；或者在 muxer 處理之前，encoder 處理之後的資料就是 AVPacket。

:::info 與gstreamer比較

在 FFmpeg 中，AVPacket 是壓縮資料的傳遞單位，結合了位元資料本身與必要的時間與附屬資訊；在系統角色上，等價於 GStreamer pipeline 中承載資料與 timestamp 的 GstBuffer，但其語意專注於編碼後的媒體資料。

:::

```c
AVPacket* avPacket = av_packet_alloc();
int err = av_read_frame(avformat_ctx, avPacket);

if(err < 0) exit(EXIT_FAILURE); // 表示讀取失敗
printf("PTS = %lf\n" avPacket->pts * av_q2d(avStream->time_base));
printf("DTS = %lf\n" avPacket->dts * av_q2d(avStream->time_base));
```

- AVFormatContext：容器的相關資訊
- AVStream：表示容器裡的媒體串流
- AVPacket：媒體串流內的資料塊
- AVRational：時間單位的定義結構

以 FFmpeg 來說，處理流程由容器層的 `AVFormatContext` 開始，解析出多條 `AVStream`；demux 後產生 `AVPacket` 作為壓縮資料單位，交由對應的 `AVCodecContext` 解碼，最終得到 `AVFrame` 作為原始音訊或影像資料。

資料讀取的起點是 `AVFormatContext`，而不是 `AVStream`，因為實際的媒體資料存在於容器中，而非單一串流。`AVFormatContext` 代表的是一個檔案、串流或連線的整體狀態，包含 I/O 來源、當前讀取位置，以及 demuxer 在解析容器時所需的前後文資訊。只有在這個層級，FFmpeg 才能持續地從資料來源讀取位元資料。

容器內的資料是交錯排放的(不是音、視訊各自連續排列)，必須依照容器內的順序解析資料，才能正確重建封包的時間關係。這個過程需要同時知道所有串流的描述與狀態，因此不可能只根據某一個 `AVStream` 來進行資料讀取。所以可以看到，`av_read_frame` 的輸入是一個 `AVFormatContext *`，然後輸出到 `AVPacket *` 之中。

## 同步音視訊
  
Frame 的時序並不是由單一 frame 自行決定，而是由容器與串流所定義的時間基準共同約束。每一條媒體流在 AVStream 中都指定了一個 time_base，用來定義該流上所有時間戳的單位。這個時間基準適用於壓縮階段與解碼階段，確保同一條流上的資料可以在一致的刻度下被解讀。

對於 `AVRational` 的定義是：

```c
 typedef struct AVRational {
     int num; 
     int den;
 } AVRational;
```

而 `AVStream::pts` 與 `AVStream::dts` 的定義都是 `int64`。在其面的代碼中，使用了 `av_q2d` 把 `AVRational` 傳換成 `double`，並通過 pts 與 dts 的資訊乘上該數值，輸出該 Frame 應該在第幾秒輸出。

|         $play_second = pts * \frac{num}{den}$         |
| :---------------------------------------------------: |
| 將 time_base 為單位的整數時間戳，換算成具體的播放秒數 |

:::warning

對於音視訊的操作，要盡可能避免再浮點數域進行處理或計算，否則會有誤差

此處將 DTS/PTS 轉為 double 秒數僅用於顯示，而非同步邏輯本身。

:::

在解碼過程中，Decoder 依據 dts 決定解碼順序，並在產生解碼後的 frame 時，保留對應的顯示時間資訊。Frame 在顯示或輸出前，會依照 pts 與音訊時鐘或播放時鐘進行對齊，從而完成 A/V 同步。只要時間基準與時間戳正確，Frame rate 不需要被明確指定，畫面仍能以正確的節奏播放。，在討論 Frame rate 與 A/V 同步時，真正關鍵的並不是 frame 本身的形式，而是時間戳的單位、順序與一致性。Frame 只是時間資訊經過解碼後的呈現結果；同步問題幾乎總是源自時間基準或時間戳處理錯誤，而非影像內容本身。

## 常見的錯誤

### 畫面抖動但音訊正常

只要相鄰 frame 的實際時間間隔忽長忽短，即使平均 fps 正確，人眼仍會察覺抖動。常見來源包括編碼端 frame pacing 不均、packet timestamp 不連續，或播放端對 PTS 的處理不一致。音訊之所以正常，是因為音訊 frame 更密集，且通常被用作主時鐘，對微小時間誤差的容忍方式與視訊不同。

### 音畫逐漸漂移

音畫一開始同步，播放一段時間後卻慢慢對不上，就很有可能是 time base 的問題。當音訊與視訊在換算時間時，使用了不同的 time base，或其中一方的 clock 有誤差就會導致。通常都是「逐漸累積」，而不是突然就不同步。只要時間戳在數值上是線性增加，但對應到實際時間的換算比例略有偏差，誤差就會隨播放時間放大。這也是為什麼單看短片段測試往往正常，實際長時間播放才會暴露問題。

### 網路丟包後畫面停住

這個問題就很單純，因為視訊的解碼器是需要前一幀的資訊才能順利解碼。對於視訊，會使用圖像群組(GOP, Group of Pictures)定義每個 I-Frame 之間的距離。如果只考慮 I / P Frame， I-Frame 就是可以獨立成像的關鍵幀，P-Frame 就是每個畫面之間的差分資訊。一旦參考資料遺失，後面的 packet 即使準時到達，也無法被正確解碼。這時播放器只能停在最後一張可解碼的畫面，直到新的關鍵幀或是正確的參考資料抵達，畫面就可以順利還原。如果對於Frame 與 GOP 想要有更多了解，[Amazon Mediaconvert](https://docs.aws.amazon.com/zh_tw/mediaconvert/latest/ug/video-quality.html#gop-structure) 的說明相當清楚，可以閱覽看看。
