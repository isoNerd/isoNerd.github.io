為何需要編碼器

2025年12月13日 · 閱讀時間約 6 分鐘
yhchen
software developer

對於視訊來說，沒有經過壓縮過後的資料仍然太大。以常見的 FHD 解析度，使用 YUV420 格式取樣，未經過編碼的大小：

FrameSize=1920∗1080∗1.5=3037.5FrameSize = 1920 * 1080 * 1.5 = 3037.5FrameSize=1920∗1080∗1.5=3037.5

一個 Frame 就趨近 3 MB，若 fps=30，一秒鐘的大小就接近 90 MB。

這個數字還沒包含音訊、封裝、網路冗餘，也沒有考慮多人傳輸。在實務上，無論是即時通訊、串流播放，或儲存錄製檔案，這種頻寬與 I/O 成本都不可接受。

所以編碼器的目標很簡單：怎麼樣在不降低影像品質的情況下，把資料變得更小一點。

空間壓縮 Spatial Compression​

在一張影像中，相鄰像素通常高度相關。牆面、天空、桌面、皮膚，大多是緩慢變化的連續區域。若為每一個像素各自記錄完整數值，會浪費大量位元。

編碼器的第一步，是把畫面切成小區塊。也就是在 HEVC(H.265) 會聽到的 Block、CU(Coding Unit)、CTU(Coding Tree Unit)，名稱不同，核心概念一致：以區塊為單位處理，而不是以像素為單位。比方說 64x64、32x32、16x16，區塊的大小越大，壓縮的速度也會越快。假設某個區塊整體亮度接近左邊或上方的區塊，只需編碼兩者的差異。這讓大量平坦區域不需要完整描述。之後進行 DCT1(Discrete Cosine Transform，離散餘弦變換)，把高頻的成分進行量化、捨棄等計算，就會留下可以重建畫面的資料。

Wiki 上對 DCT 頻譜套用不同濾波器的範例

對於每個 I-Frame 來說，都可以獨立解碼(不需要依賴其他的 Frame)。從邏輯上來看，可以把 I-Frame 當成 jpg, png 來類比：

  • 只用空間壓縮，不依賴其他 frame
  • 可以單獨解碼
  • 是畫面重建的起點
  • 畫質由量化程度決定

在「不考慮封裝與參數缺失」的前提下，I-frame 的角色接近一張高度壓縮、沒有檔案語意的 JPG。如果未來有講到 WebRTC 的文件，就可以理解 FIR/PLI 請求的用途。

時間壓縮 Temporal Compression​

時間壓縮的概念很好解釋，考慮到連續的 frames 長得很像要怎麼處理。舉一個極端的例子就是，拍攝了一個一分鐘的影片，但是每一秒的畫面都一模一樣。

在影像中，大多數的情況都是「原有的畫面加上一點小變化」。舉例來說，如果拍攝「鳥在山上飛行」，背景的山幾乎都是不變的，只有前景的鳥在飛行。如果每一幀都完整編碼，等於反覆儲存幾乎相同的內容，時間壓縮就是要避免這種重複。

編碼器會選擇一張已存在的 frame 當作參考，然後嘗試計算「新的畫面，是怎麼從前一個畫面繪製過來的？」。這個計算不是像素層級，而是區塊層級。在新畫面中，對每個區塊，找出它在參考畫面中最相似的位置。這個位移向量，就是 motion vector。如果鳥在畫面上往右移動 5 個像素，編碼器不會重畫整個鳥，只記錄「這個區塊來自上一幀的某個位置，再加上一點修正」。

備註

HVC / HEVC 描述的「幀間編碼2」、「運動補償3」、「運動估計4」，其實就是在描述時間壓縮如何被具體實作。 幀間編碼定義了 frame 之間如何建立參考關係；運動估計在編碼端找出區塊在參考畫面中的來源位置；運動補償則在編解碼兩端，依照這些資訊重建預測畫面，再以殘差修正差異。

且 Picture 是比 Frame 更加廣泛一點的術語，可以同時

這就是為什麼 Frame 要區分成 I / P / B 三種 Frame

  • I-Frame(intra-coded picture)
    • 完整的影像，就像是 JPG 或是 BMP 圖片檔。因為可以獨立解碼，所以被稱為 Keyframe。
  • P-Frame(Predicted picture)
    • 單向預測幀，僅包含影像相對於前一幀的變化，因此也被稱為 Deltaframe。
  • B-Frame(Bidirectional predicted picture)
    • 雙向預測幀，使用前後參考畫面進行雙向預測的幀間畫面，能提供最高的壓縮效率。
Wiki 上，I / P / B 三個 Frame 的組成範例
提示

圖像與幀在視訊標準中，picture(圖像) 是比 frame(幀) 更泛的概念，一個 picture 可能是完整畫面（frame），也可能是交錯掃描下的半張畫面（field）。frame 代表完整影像；field 只包含奇數或偶數掃描線，交錯掃描時，一個 frame 由兩個 field 依序組成。

在幀與時間戳，提及過 PTS 與 DTS 會不相同是因為存在 B-Frame。這裡也補充一下，在串流系統中，B-Frame 一定會增加延遲，因為編碼與解碼流程必須：

  • 先取得未來的參考圖像
  • 再回頭解碼當前的 B-frame
  • 顯示順序與解碼順序不同（frame 重排序）

釐清了不同 Frame 的概念，就可以知道為什麼只要 P / B Frame 遺失，就要等到下一個 I-Frame 抵達畫面才能重建。本質上就是因為 Frame 有明確的依賴關係，而 B-Frame 的存在導致 DTS 與 PTS 會不一樣，所以還有重新排序的行為。

兩者如何分工​

空間壓縮與時間壓縮解決的是不同層次的問題，共同構成視訊編碼的基礎。

對於「編碼後的資料大小」，主要都是時間壓縮決定的：利用連續畫面之間的相似性，決定哪些畫面可以只描述差異。空間壓縮的範圍只在單一畫面內，決定每張畫面需要多少位元才能被重建。它不引入 frame 之間的依賴關係，因此延遲可預期，錯誤影響範圍受限。

當系統關注的是即時性、穩定性，或需要快速從錯誤中恢復時，空間壓縮的比例會相對提高。在不同系統中，調整編碼行為的本質不是「開或關某個功能」，而是選擇依賴多少時間壓縮、承擔多少系統複雜度。

低延遲通訊、直播系統會刻意限制時間壓縮(關閉 B-Frame、GOP 大小調整)，播放、錄製與點播場景則會充分利用它(降低儲存大小)。所有設定其實都可以回到這個核心問題來理解：系統願意用多少結構複雜度，換取多少位元率效率。
